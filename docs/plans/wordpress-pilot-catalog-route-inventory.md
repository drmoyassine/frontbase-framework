# Configured source catalog URL inventory

2026-10-10. Bounded internal collector following the [preparation serialization guard](wordpress-pilot-preparation-url-serialization.md) and [active-capture audit](wordpress-pilot-active-capture-route-audit.md). No endpoint, admin control, live datasource query or publication change is included.

## Purpose and boundary

The existing directory preview excludes institutions without a scoped city and programs without a scoped institution/city. It converts invalid original URLs to null and bounds ordinary list results. Those are presentation queries, not sufficient evidence that every WordPress listing is represented. The new `packages/backend/src/compat/catalog-route-inventory.ts` queries configured institution/program/article identities and paths separately. Relationship checks are selected evidence rather than WHERE exclusions: orphaned listings remain visible to the inventory.

This is a reusable internal backend helper, not a USA template hardcode or a new product package. The caller must authenticate the principal and resolve the datasource under the same owner before supplying the query callback. The helper checks matching owner context; it cannot independently authenticate the caller or certify ownership of an arbitrary supplied runner. It is not registered in the API, exported from the package root, included in the public query manifest, or wired into the Pages dialog. Existing preview, active-capture audit and publication behavior remain separate.

## Read and result contract

Strict existing configuration/readiness is required. SQL identifiers come only from validated mappings; country/scope values, article role/origin and fixed limit are parameters. Institutions/programs are included regardless of parent integrity. Articles retain the existing configured scope, `article` content role and exact source-origin restrictions; an unconfigured article collection is explicitly absent from `configuredRoles`. Cities and countries have no configured preserved public route here and are not emitted as pages. No publication-status filter is applied: `configured-source-catalog` describes configured source records, including records already represented in a capture.

Projection is limited to IDs, original paths, returned scope and relationship evidence, plus article role/origin for revalidation. No title, description, body, media, provider agreement or credentials are selected or returned. Extra driver columns are ignored. Returned foreign scopes, inappropriate article role/origin, invalid or duplicate family identities, malformed relationship evidence and more than 1,000 total records refuse with constant errors. SQL requests at most 1,001 per family; total overflow is never silently sliced. Adapter-returned arrays are validated after the query returns: this is not a transport streaming or memory-size guarantee.

Each record reports its family, ID, local original path or null and explicit problems: missing original path, invalid original path, browser pathname spelling change, and/or missing scoped parent. A null original path is not automatically a migration gap: expanded Supabase records may never have had a WordPress URL. Fresh WordPress evidence is required to determine whether a particular original is missing. Duplicate paths are retained for subsequent collision auditing; duplicate IDs refuse. Original supported paths are not renamed, encoded or trimmed. Absolute URLs must match the configured origin plus the extracted path exactly, preventing URL parsing from hiding traversal or silently changing an absolute spelling. Unsafe invalid URLs are not echoed.

The result sets `stableSnapshotVerified: false` and `publicationAvailable: false`. It does not compare source reads, acquire a database snapshot, validate saved configuration revision, compare WordPress exports, import records, approve articles, activate a capture or grant installation. It must not be marketed as full migration coverage. A catalog above the temporary 1,000-record bound needs a separately verified bounded snapshot/export or pagination design before integration; list pagination alone cannot certify completeness under concurrent changes.
