## Operator rollback protocol

1. Record exact account/team/project/environment, current canonical candidate and intended predecessor. Inspect their actual target/readiness and state binding; refuse ambiguous/mismatched identities.
2. Establish schema/backward compatibility and a verified backup before any state-changing deployment. Test the predecessor against the existing state/session and public content first. An older code artifact cannot repair incompatible migrated data.
3. Use the provider's explicit code rollback only for the reviewed candidate. Do not fetch or restore remote secret values, delete provider resources, auto-replay jobs or treat partial environment updates as rolled back.
4. Inspect the resulting alias/version and verify session, saved pages and published content. An uncertain command result requires read-only provider reconciliation before another write. Restore/promote the previously recorded original candidate only after checking current provider truth.
5. Reconcile the managed local journal separately. Vercel operation resume proves recorded upload completion, not current alias ownership. Cloudflare's managed identity includes deployment ID: an out-of-band rollback/forward deployment can intentionally invalidate its local identity even if the code version returns to the original. Generic CF rollback/journal adoption is not implemented or live-tested here; do not edit its journal by hand to bypass drift refusal.

[Cloudflare version boundaries](https://developers.cloudflare.com/workers/versions-and-deployments/) exclude underlying storage state. [Vercel Instant Rollback](https://vercel.com/docs/instant-rollback) restores a prior build/configuration rather than later project environment edits. [Native source/store parameters](https://vercel.com/docs/deploy-button/source) require provider-supported references and exact product identifiers.
