# Supabase OAuth Connect + Postgres State-DB in the Deployment Wizard

Owner-approved 2026-10-29. Decision record: [DECISIONS.md 2026-10-29](../history/DECISIONS.md). Branch: `reconcile/public-baseline-20261028` (clean worktree; the OneDrive checkout belongs to another stream and stays untouched).

## Goal

1. A **Connect Supabase** button in the shared bindings editor and console settings, using the Supabase Management API OAuth2 authorization-code flow, as a third provider in the existing `provider-oauth` protocol alongside Cloudflare and Vercel.
2. A **Supabase/Postgres state-db adapter** in the deployment wizard manifest, with connect mode (scoped-role DSN) and create/reuse modes (isolated `frontbase_edge_*` schema + scoped role, reusing the Edge Databases provisioning SQL and `SupabaseProvisioner`).
3. Per-host runtime transport: Hyperdrive binding on Cloudflare via `postgresStateRunner`; direct PostgreSQL on Vercel/Docker/Node. D1 stays the Cloudflare default.

## Existing surfaces being extended (no new mechanisms except refresh)

- `packages/backend/src/provider-oauth.ts` — auth-code + PKCE S256 flow, one-use claims, provider account verification via a real management call.
- `packages/backend/src/provider-oauth-config.ts` — env-driven client config loop `FRONTBASE_{PROVIDER}_OAUTH_*`.
- `packages/backend/src/provider-oauth-import.ts` — one-time grant handoff (provider allow-list).
- `packages/backend/src/provider-oauth-bindings.ts` — reserved `oauth/` secret-reference resolution (currently cloudflare-only; pattern for supabase consumers).
- `packages/edge-core/src/deployment.ts` — adapter manifest (`state-db` role currently SQLite-family only).
- `packages/edge-infra/src/providers/postgres-state.ts` — `postgresStateRunner` (schema isolation, self-heal, Hyperdrive/direct URL) — already runs the shared migrations on Postgres.
- `packages/edge-infra/src/provisioning/supabase.ts` — `SupabaseProvisioner` (schema-per-resource).
- Console: `bindings-form.ts` (`providerConnections` union), `provider-connect.ts`, `ConnectProviderDialog.tsx`.

## Phases

### Phase 1 — provider-OAuth protocol extension (backend only)

- `OAuthProvider` union + `providers` array + `endpoints` map: add `supabase` → authorize `https://api.supabase.com/v1/oauth/authorize`, token `https://api.supabase.com/v1/oauth/token`.
- `/start`: supabase branch builds the standard authorize URL (client_id, response_type=code, scope, redirect_uri, code_challenge S256).
- `/finish`: send `code_verifier` for supabase (PKCE) in addition to cloudflare; `client_secret` when configured (confidential clients).
- Account verification: `GET https://api.supabase.com/v1/projects` with the Bearer token; map to `{id: ref, name}`; same ≤50 shape validation. A management call proves usable authorization (same principle as the Cloudflare/Vercel branches).
- `provider-oauth-config.ts`: iterate `['cloudflare','vercel','supabase']`.
- `provider-oauth-import.ts`: allow `supabase` grants.
- Relay (`provider-oauth-relay-target.ts`): both policies admit `supabase` for `purpose:'connect'` only (it is a resource provider, never an install host); enrolled-origins/receiver gates apply unchanged. Required because the operator's Supabase OAuth app registers `https://oauth.frontbase.dev/api/provider-oauth/supabase/callback` — the shared relay — as its redirect URI.
- Tests: `test/provider-oauth.mjs` supabase connect cases (unconfigured 409, full start→finish happy path with fake token endpoint, state/cookie/claim refusals); `test/provider-oauth-mutation.mjs` gates for the supabase branch (fault: dropped code_verifier / dropped account fetch → named FAIL).

### Phase 2 — token refresh + revoke (the one new mechanism)

- New module `provider-oauth-refresh.ts`: given a client + stored authorization, if `expiresAt` passed and `refreshToken` present, POST `grant_type=refresh_token` — per the official guide, refresh uses the **same** `POST https://api.supabase.com/v1/oauth/token` endpoint as the code exchange (no separate /refresh path). Return rotated authorization (Supabase rotates refresh tokens). Revoke on disconnect. Verify live during Phase 6 whether Supabase requires the `client_secret` as a Basic-auth header (per guide) in addition to/instead of the form parameter the current exchange sends.
- Vault: add atomic rotate-by-connection-key (`save` stays create-only; rotation replaces under the same key with owner checks).
- Consumers call refresh before use; `reconnectRequired` only when refresh is impossible (revoked/expired-sliding-window).
- Tests + mutation gates: refresh rotation, refresh-failure → reconnectRequired, revoke-on-disconnect, no-leak (tokens absent from responses/logs).
- **Delivered 2026-10-29:** `provider-oauth-refresh.ts` — `refreshOAuthAuthorization` POSTs `grant_type=refresh_token` to the same `/v1/oauth/token` as the exchange (client_secret as a form parameter exactly like the exchange, so the live-round form-vs-Basic correction lands in both places at once; rotating refresh tokens replace the stored one, an absent response token keeps it for non-rotating providers; `expires_in`→`expiresAt`; same bounded reader, bearer/length validation, opaque errors), plus a 30s guard so a near-expiry token never starts a doomed request. `revokeOAuthAuthorization` implements the Management-API spec revocation — `POST /v1/oauth/revoke` JSON `{client_id, client_secret, refresh_token}` (all required, 204) — for supabase only; no verified revocation endpoint exists for cloudflare/vercel yet, so those return false honestly and the provider dashboard stays the certain path. Vault `save` stays create-only; a new optional `OAuthVault.replace(key,expected,value)` primitive powers atomic rotate-by-connection-key (`providerOAuthVault.refresh(clients,deps)`): rotation replaces the record only while it still equals the inspected value, a concurrent rotation is adopted by re-reading, and grants that cannot be refreshed are omitted (so `/status` keeps reporting `reconnectRequired` truthfully). Bootstrap hosts (hosted-cloud `resolveCredentials` + apply-time handoff envelope, docker host both call sites) now refresh-before-use — the installed-app handoff never ships a dead token; the D1, Vercel-env and file-based vaults each implement `replace`. Disconnect (`DELETE /api/edge-providers/{id}`) attempts best-effort revocation before deletion and always proceeds — a provider or network failure never traps a credential the tenant asked to remove. The relay default `/privacy` sentence about refresh/revocation was updated to match; the deployed production relay shows the new text only after its next deploy. Gates: `provider-oauth.mjs` PASS (rotation/race/failure/duplicate-save/revoke-contract/installed-app disconnect incl. failure-tolerant delete), `provider-oauth-mutation.mjs` PASS 15/15 (5 new), relay suites + docker-host suites + compat-security/parity-foundation/tenant-matrix/conformance + `test:hosted-bootstrap` + `pnpm -r check` + cf-full build PASS. Found while wiring consumers: the relay **client** and the relay `/connect` consent page still hard-refuse supabase (the phase-1 widening covered the admission policies only), so a relay-configured installation cannot start a supabase connect — **fixed in the immediate follow-up commit** (relay-client start/finish/callback/status + relay /connect widened; end-to-end supabase relay-connect flow and two new mutation gates green; the deployed production relay needs its next deploy to serve it live).

### Phase 4 — wizard state-db adapter

- `edge-core/deployment.ts`: new state-db adapter entry `supabase-postgres` — targets cloudflare/vercel/docker; modes connect/create/reuse; configKeys (url or project ref, schema), secretKeys (role password); D1 remains default.
- **PostgREST connect mode (owner requirement 2026-10-29, DECISIONS.md):** connect accepts either a wire-protocol DSN or a PostgREST endpoint — the `postgrest` transport reuses the existing CF-20 `supabaseRunner`/`supabasePostgrestClient` (SQL over PostgREST RPC via the documented `execute_query` database function) for self-hosted Postgres without wire reachability. The helper-function prerequisite is stated in the wizard; the mode is labeled HTTP-per-statement, not throughput-equivalent.
- Wizard form card + review validation (bounded, no provisioning during review).
- Apply-time: create/reuse via existing provisioning SQL; worker receives only the scoped-role DSN (or PostgREST endpoint+credential), never the PAT/OAuth grant.
- **Delivered 2026-10-29 (provisioning core, tested module — not yet wired or exposed):** `scripts/deployment-setup/supabase-state-provision.mjs`. `planSupabaseStateProvision` is the pure planner (projectRef pattern, `frontbase_edge_*` schema pattern, ≤63-char role fence, token secret-ref required, `defaultSchema` fallback); `provisionSupabaseState` runs the Edge Databases SQL verbatim over the Management API — create = emptiness check then schema+scoped-role+grants; reuse = existence + emptiness checks then role re-arm with database-wide CONNECT/SEQUENCES grants (password minted per run, base64url). Its return value is a transformed prepared profile whose state-db binding is the standard connect-wire selection (`db.<ref>.supabase.co:5432/postgres` + schema) with only the scoped-role credential — the PAT/OAuth token is deleted from the transformed credentials and the input profile is never mutated. Suite `scripts/test-supabase-state-provision.mjs` + mutation gate `scripts/test-supabase-state-provision-mutation.mjs` (4 faults), both wired into `test:deployment-setup` (full chain PASS). Edge-core modes deliberately stay `['connect']`: the hosted/native bootstrap forms fall back to `adapter.modes` without a capability map, so declaring create/reuse would advertise them before any executor provisions. **Still open in phase 4:** executor wiring (cloudflare: provision past the preflight, transformed profile into lowering + the Hyperdrive trigger, `resources.database` receipt; docker bootstrap host likewise), then exposure (capability maps; the CF review checks for state-db create/reuse still assume D1 names/UUID refs and need per-adapter variants).
- **Delivered 2026-10-29 (executor wiring + exposure — phase 4 complete):** edge-core registers create/reuse (`configKeysByMode` keeps the wizard honest: connect shows url/schema/host/port/database, create shows projectRef/schema, reuse shows projectRef; mode switches prune stale transport fields) and validates them (projectRef + fenced `frontbase_edge_*` schema name + token reference; transport parts and role credentials in a provisioned selection are `state_transport_conflict`; D1's resourceName create rule stays D1's). The Cloudflare executor provisions past every refusal preflight — the Management-API DDL runs after the worker/D1/KV/R2 preflights, then `profileEnvironment` and the Hyperdrive trigger consume the **transformed** connect profile (the reviewed provisioned shape never lowers; the generic external probe is skipped for provisioned bindings because the DDL preflight verified emptiness), the receipt records `resources.database` (schema name) and the Hyperdrive config, and the runtime manifest embeds the transformed binding. `cloudflareExecutionIssues` keeps D1's fixed-name/UUID contract for D1 and applies the schema-name rule to supabase; `verifyEmptyCloudflareResources` only inspects Wrangler-discoverable D1/KV. The docker bootstrap host provisions in `apply` and boots from the transformed profile — the operator token never reaches the mounted runtime volume; a re-apply after a failed boot re-runs the idempotent DDL (IF NOT EXISTS + role re-arm). Vercel's wizard still hides the adapter entirely (its capability map has no supabase entry — adding connect there is a separate, larger claim). Gates: edge-core `deployment.mjs` 21/21 (2 new) + `deployment-mutation.mjs` 7/7 (new provisioning-fence fault); executor suite (create happy path with exact Management-API headers/DDL, minted-DSN Hyperdrive argv = lowered APP_DB_URL, token absent from argv/stage/receipt, reuse 3-call re-arm without CREATE SCHEMA, occupied/vanished refusals before any host write, review-check cases) + execution mutations 22/22 (4 new: create admission, provisioning call, probe skip, state receipt; the phase-5 single-mode admission fault was superseded); docker host suite (supabase create → active installation, encoded role DSN in the boot env, token absent from runtime.json, probe skipped) + 6/6 mutations; provision gate 4/4; `test:deployment-bindings` 24/24; console `check` PASS; full `test:deployment-setup` and `test:hosted-bootstrap` chains PASS; `pnpm -r check` PASS.

### Phase 5 — runtime transport + host wiring

- Cloudflare native deploy: create/bind Hyperdrive with the scoped-role pooler DSN (extends existing native resource creation); `postgresStateRunner` consumes the binding.
- Vercel/Docker: direct role DSN.
- PostgREST transport: host-independent plain HTTPS (no Hyperdrive/wire access needed) — the one mode that runs unchanged on every target.
- Migrations self-apply on first boot (already portable across SQLite/D1/Turso/Postgres).
- **Delivered 2026-10-29 (transports, minus CF-native Hyperdrive creation):** the wizard lowers `supabase-postgres` connect through `profile-environment.mjs` — PostgREST as `APP_DB_POSTGREST_URL`/`APP_DB_POSTGREST_TOKEN`(+`APP_DB_POSTGRES_SCHEMA`) identical on every target; wire as a credential-encoded `postgres://` DSN in `APP_DB_URL` on docker/vercel only, with `state_wire_requires_hyperdrive` refused on cloudflare until native Hyperdrive creation exists (fail-closed, never a silent boot failure). The host resolver (`examples/cf-full/src/state-db.ts`) gained two kinds: `postgres-postgrest` (CF-20 `supabaseRunner`, https-only, any host) and `postgres-wire` (`postgresStateRunner`; refused on deno/cloudflare without cloud-mode Hyperdrive — no TCP there); half-configured or ambiguous selections fail loud naming the vars, and DSN/bearer values never reach labels, `displayUrl`, or cards. The empty-state probe (`cloudflare-state.mjs`) probes the application schema (`pg_tables`, quote-doubled, default `public`) via the matching runner for both transports. Schema identifiers tightened to lowercase in the manifest validation to match `postgresStateRunner`'s quoted-identifier rule. Still open under phase 5: Hyperdrive create/bind for CF-native wire deploys (currently refused by name), and the apply-time create/reuse executor (phase 4 remainder).
- **Delivered 2026-10-29 (CF-native Hyperdrive, completing phase 5):** the Cloudflare executor now admits `supabase-postgres` connect (PostgREST lowered like any HTTP adapter — no Hyperdrive, no D1) and provisions wire: `executeCloudflareFirstInstall` creates a Hyperdrive config (`wrangler hyperdrive create <app>-state --connection-string <reviewed DSN> --caching-disabled`, identity parsed and journaled like the KV/R2 steps), appends the `[[hyperdrive]]` binding to the staged config, and records it in the receipt; SQL-response caching is off so application state reads its own writes. `profileEnvironment` refuses cloudflare wire for every caller except the native executor and its empty-state probe (`nativeHyperdrive` option) — under the executor it additionally lowers `APP_DB_HYPERDRIVE=1`, a new explicit resolver opt-in that opens the Hyperdrive binding **without** cloud mode (cloud mode stays the hosted platform's marker and requires its tenant zone; the bare binding still adopts nothing, preserving the committed-wrangler.toml self-host rule), while the DSN keeps lowering as the loud no-binding refusal. Gates: `test:state-db` (new native-opt-in precedence, binding-missing fail-loud, no-leak) + new `test:state-db-mutation` (2 faults) wired into contracts.yml; executor suite (Hyperdrive happy path + create-failed/bad-identity faults + PostgREST path) with 4 new execution-mutation faults (19 total); state-transport mutations 6/6; full `test:deployment-setup` and `pnpm -r check` PASS. ## Non-goals / boundaries

- No Supabase OAuth requirement for self-host (PAT fallback is supported and documented).
- No vector/cache/queue adapters from the console Edge Databases feature in the wizard v1.
- No hosted-broker dependency introduced; the existing explicitly-configured relay remains the only shared callback infrastructure.
- No GA/parity claims; independent-account verification remains an open gate.
