# B: template installation, recovery and upgrade contract

**2026-10-08. Primary design proposal and bounded private proof; not a public importer.** Implements the next review task in the [execution plan](wordpress-pilot-execution-plan.md). Existing admin, six framework packages, trusted deployment owner and one engine remain the product boundary. Final template packaging and production adoption still require their acceptance work.

## Required behavior

An administrator connects the destination's database/storage, chooses a template and supplies site identity, scope, field mappings and routes. Preflight shows the complete changes before writing anything. An install creates editable draft pages and shared configuration; it does not import canonical rows, create relationships/provider agreements, approve content or publish. A separate-country deployment receives its own engine/state/domain and bindings.

The exported artifact contains versioned configuration defaults and editable layouts only. Credentials, datasource configurations/IDs, users, canonical rows, review/approval/capture/pointer/recovery state and resolved deployment origin/scope are excluded. A typed strict bounded artifact, framework schemas and complete rebound layouts must validate before writes. Production package layouts should come from the existing template generators and reviewed presentation, not a second maintained rendering system; B's hand-written synthetic layouts demonstrate the contract only.

## Preflight and durable operation

1. Obtain the trusted owner and administrator role from the existing authenticated request. No owner, actor, capabilities or receipts are trusted from the import body. Discover actual owner-scoped datasource kind, schema/mappings, storage and current configuration/page state. A nonempty datasource string is not capability proof.
2. Validate artifact/version/exclusions/limits and destination bindings. Check the complete page/query grammar, required tables/columns and preview readiness without mutating shared settings. Reject reserved/admin/API routes, duplicate role/slug/node identities, unsafe paths and all unowned page/configuration collisions, including soft-deleted slugs. Matching bytes do not establish ownership.
3. Freeze an exact digest over artifact plus destination-bound configuration and pages. Record a server-owned operation ID, owner, digest, expected configuration revision, exact page IDs/hashes/metadata, status and step intents/receipts. The artifact never carries this state. An operation-ID retry with changed content/bindings is a conflict.
4. Reserve the entire installation namespace/owner operation before writes. Settings and page mutations must be transactional where supported, or use durable per-step reservation/conditional writes with explicit incomplete state. Optional `DbRunner.transaction` is not a uniform cross-driver promise: SQLite/D1 paths must be proven or refused as unsupported for the chosen atomic contract. Reuse framework stores/validators rather than bypassing them with a public SQL importer.
5. Write only conditional on preflight state. A known receipt permits a retry to keep an exact operation-owned page and create only missing pages. A complete receipt permits a no-op. Owner edits, changed revision, renamed/deleted/replaced/published pages and unowned identical pages stop recovery. Never increment configuration revision on a no-op.
6. Persist intent before a mutation and its verified receipt after success. A crash/lost response between those points is **uncertain**. Read-back may show what exists; it does not prove who wrote it. Do not blindly replay or adopt it. Resolve using server transaction/operation evidence, or present explicit operator reconciliation. No automatic lease expiry should authorize a second writer while the first may still run.

The private [recovery planner](../../examples/education-template-proof/src/recovery-plan.mjs) evaluates trusted snapshots/receipts and returns create/keep/conflict tasks without writes. Its owner/capability facts and receipt are trusted fixture inputs. It does **not** provide the durable operation store, namespace reservation, authenticated HTTP adapter or execution coordinator above; it must not be exposed directly with client-supplied facts.

## Upgrade and recovery

Produce a reviewed three-way proposal from the exact installed baseline, current owner layout and next artifact. Preserve owner text/styles/root metadata, added/nested content, deletions and changed content removed from the newer template. Unchanged owned nodes may upgrade. A new template ID colliding with an owner node or an owner reorder requiring reconciliation returns the unchanged live layout with a conflict, not a partially merged applicable result. Validate unique node identities/grammar in all three inputs before a production proposal.

Before applying, save the existing page history/recovery snapshot and use a page/configuration hash/revision predicate so intervening edits cannot be overwritten. Existing page PUT/layout endpoints do not take an expected hash; a read followed by unconditional PUT is not a safe upgrade. Extending a conditional store/route is a production prerequisite, not permission for this example to bypass it. A rollback/restoration must be equally conditional and preserve subsequent owner edits. Do not auto-delete created pages or reset settings as compensation after failure: those resources may already have owner edits.

## Acceptance boundary and ordered follow-up

Local synthetic proof covers strict artifact exclusions, two independent destinations, known partial/completed retry plans, ambiguous/collision refusal and conservative customization proposals. It does not prove atomic production installation, restart-safe journals, hosted concurrency, conditional application/rollback, polished packaged layouts, no-code installer UI or registry/clean-room install. No actual pilot install or publication is performed.

Order for production delivery: server operation ownership/reservation and driver-specific atomic-or-durable protocol; page hash/revision CAS and recovery; import/preflight/confirmation UI inside existing admin; existing-template-generator package and customization upgrade; clean install/edit/preview/exact-reviewed publish/rollback on a separate-country deployment. D inquiry handling can be reviewed next without representing this installer gate as closed. Off-server backup remains owner-deferred and blocks production acceptance. Framework Developer Preview remains recommended subject to R0–R4; no release scope/label decision is made here.
