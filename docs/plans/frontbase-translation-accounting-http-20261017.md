## Reuse and compatibility

[Accounting adapter](../../packages/translation/src/adapters/postgrest-accounting.ts) extends the existing typed job adapter with an explicitly negotiated accounting protocol. The original job adapter/factory and job protocol version1 remain usable without accounting installed. Accounting initialization first verifies the job protocol, then requires accounting1/jobProtocol1; absent, unknown, malformed or failed capability responses leave accounting unavailable. No silent downgrade/fallback or installation request. Strict inputs and returned owner/key/state/cost checks reject mismatched data, and remote transport/validation failures have fixed error text.

The [shared host HTTP bridge](../../packages/edge-infra/src/translation.ts) builds both adapters from the same Supabase/PostgREST client, schema, credentials, injected fetch and native-root/Supabase-path conventions. There are only two finite RPC names: translation_request and translation_accounting_request. No SQL text, socket, pool, SDK dependency or new credential store enters the translation runtime. [Owned host resolution](../../packages/backend/src/compat/translation-storage.ts) shares the existing datasource/account/guard resolution; configuredTranslationAccountingStorage resolves fresh saved credentials and trusted project identity and verifies both capabilities before returning. Current connection-check/settings behavior remains job-v1 compatible and read-only; it does not infer accounting readiness or write permission.

[Additive administrative SQL](../../packages/translation/sql/postgrest-accounting-v1.sql) adds accounting_protocol, allowances, attempts and one finite SECURITY INVOKER dispatcher in translations. Install base postgrest-v1.sql first, then this addon. The addon refuses unsupported existing protocol versions, including unknown future accounting metadata, without overwriting it. Reinstalling the base may reset table grants: reapply the supported addon afterward and verify both capabilities. Installation/upgrade is an administrative operation, not runtime behavior or a generic SQL endpoint. No existing owner data is migrated by this task.

Accounting mutations share the EXACT existing job/revision project advisory transaction lock. Database-clock lease/source/head checks precede reservation and dispatch. Budget/request/concurrency aggregates use scoped indexes. Dispatch calls the existing v1 dispatch operation and updates the attempt in the same database transaction; any later failure rolls back both. Immutable allowances, one-time dispatch, stable settlement, full uncertain holds and no post-dispatch refund match the shared reference contract. RLS is enabled; the server role has no BYPASSRLS, visitor roles cannot execute the accounting function, allowance UPDATE and attempt DELETE are withheld. The privileged server credential spans projects: the host must derive trusted scope; it is never a visitor/App Users credential.

Lock behavior follows [PostgreSQL’s transaction-level advisory-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS), verified here on PostgreSQL17.11. The Supabase changelog Markdown endpoint could not be rendered by the documentation tool; this implementation changes the standalone SQL protocol/client composition rather than hosted Supabase features.

## Reproducible proof

[One shared conformance suite](../../packages/translation/test/accounting-conformance.mjs) runs against injected SQLite, the typed HTTP adapter backed by SQLite and real PostgREST/PostgreSQL. It covers caps, stable reservation/settlement, lease checks, release/cancellation, uncertain cost, source/manual conflict charging, runner denial/completion, scope and invalid costs. Physical SQLite restart remains a separate reference-provider test.

[Disposable local runner](../../scripts/localization/run-accounting-postgrest.mjs) requires a local Docker context, uses official postgres17.11-alpine and postgrest14.18 images, an isolated network, tmpfs data and a loopback-only port, and creates random fixture-only credentials. Setup uses docker exec/psql strictly as an administrative fixture; application operations are HTTP RPC calls. Labels and exact resource names are verified before cleanup. It never reads an owner credential or reaches studygram-selfhost. Official image caches remain; both temporary containers/network and their tmpfs data are removed.

The real [HTTP suite](../../packages/edge-infra/test/accounting-postgrest-live.mjs) runs the shared contract, eight concurrent reservations and eight concurrent dispatches, duplicate settlement, owner reads, strict raw SQL-contract inputs, anonymous refusal and a trigger-forced failure after job dispatch. The failure leaves the attempt reserved and job undispatched, proving atomic rollback. Three real SQL faults are detected: removed allowance bound, allowed post-dispatch refund and missing shared lock. The lock fault injects a fixture-only pause to force overlap; restored SQL passes again. An unknown future accounting version is refused at installation. Nine fixture tables have RLS, public contains zero objects, server BYPASSRLS is false, anonymous EXECUTE is false, allowance UPDATE and attempt DELETE are false.

The adapter enforces HTTPS for real deployments. The local proof deliberately maps only two fixed synthetic HTTPS RPC URLs through an injected test transport to loopback HTTP. This certifies real SQL/PostgREST behavior, not TLS, deployed Cloudflare execution or the backend SSRF guard; those boundaries have separate retained tests. No native PostgreSQL client is used in the application runtime.

An initial SQL CASE expression needed parentheses before the first PostgreSQL installation passed. That failed fixture cleaned all its resources. Final accepted proof reruns the corrected/strengthened SQL from scratch, including protocol-version refusal; no failed installation is presented as passing evidence.
