# WordPress to Frontbase migration pilot

**Date:** 2026-10-04. **Status:** USA source inventory, private preservation and local draft implemented; canonical reconciliation and production acceptance remain open. **Pilot:** study-in-usa.com, owner selected local draft first. **Data source:** Studygram DB, Supabase project `uwzosvzynnpbxpnwqgkm`, MCP verified. UAE/other domains remain unaudited for migration.

## Purpose and release boundary

Use the eleven existing WordPress installations as real adoption evidence for Frontbase. Deliver one verified replacement before repeating the process across the portfolio. Preserve the six reusable package boundaries and one-engine model. Generalize console/builder improvements only from demonstrated migration needs; site-specific content and branding belong in consumer projects.

The owner wants a fresh Frontbase design and a larger USA catalog. Preserve every original WordPress listing and its URL while adding reviewed Supabase records. WordPress template conversion is outside scope. Interpret the owner's “cash” item as caching/cost controls pending clarification.

This plan supports [R0](../history/PUBLIC-RELEASE-AUDIT.md), the [release strategy](../history/PUBLIC-RELEASE-STRATEGY.md), and the proposed [competitive roadmap](competitive-roadmap.md). It does not complete R0, reactivate CF-22, accept new architecture, or change launch scope. The recommended first framework label remains **Framework Developer Preview**, subject to owner acceptance and existing release gates. A successful private migration is additional evidence, not a public-release declaration.

## Inspected implementation and limits

### Owner clarification: reusable, admin-configurable features (2026-10-05)

USA is the proving consumer for one reusable directory/content template. Another destination, for example Hungary, must be configured through Frontbase administration without a template code fork. This is a consumer-feature acceptance requirement; it does not adopt a new package architecture, reactivate CF-22, change the accepted public release scope, or establish competitive superiority.

The target template contract separates reusable layouts/components and collection roles (institution, program, city, article, taxonomy, media) from each site's datasource/field mappings, explicit relationships, server-enforced publication scope, record URL mapping, branding, locales, contacts and deployment configuration. Studygram country IDs, domain names, SQL tables and WhatsApp/email values belong in site configuration. Country filtering controls the catalog selection; it is not a substitute for tenant authorization or an approved publication allowlist. Original routes are namespaced by source site and explicitly preserved; new-record route patterns remain configurable.

Required admin surfaces: datasource/table/field and relation mapping; country/site scope and approved collections; search/filter/sort/pagination settings; reusable listing/institution/program/article layouts; cover/logo/gallery bindings and fallbacks; rich content/taxonomies/media; URL/SEO/sitemap controls; CTA/form destinations and workflows; preview, validation and existing publication/deployment controls. Extend inspected datasource selectors, data/repeater binding/filter editors, WordPress wizard and page/publication flows within their owning packages. Inventory their actual capabilities before extending them; component/file existence does not prove the full end-to-end workflow.

The local draft currently proves a reusable primitive layout and bounded relational browsing. Its USA projection, snapshot data selection and injected GET filters are consumer scaffolding, not the finished admin configuration/publishing feature. Extract demonstrated gaps into typed, validated contracts and reusable controls; keep source extraction/recovery scripts as migration tooling. New schema/runtime/release architectural choices still require the canonical decision process.

Acceptance: an admin configures USA, saves/reloads it, then creates a second destination configuration using the same template/component implementation; expected destination records, relationships, media and original routes render correctly without source edits. Preview/publication/export must use the same approved collection scope and engine contracts. Negative tests must reject cross-tenant access, leaked private fields and query attempts to widen the configured scope. Article editing/publishing and original URL preservation must work through the console; copied materialized snapshots alone do not satisfy this requirement. Published versions remain stable until an administrator accepts a template/configuration update; version/upgrade behavior must be implemented and verified before being advertised.

## SEO and cutover acceptance

Keep existing domains and user-visible paths wherever practical. Build an original-to-target URL ledger from source content, stored permalinks, sitemaps, internal links, access logs and Search Console exports. The currently broken live site is not a sufficient baseline. Distinguish intended source behavior from existing outages and malicious/spam content.

Every inventoried public URL needs an explicit disposition: equivalent 200 page, direct permanent redirect to a relevant equivalent, or reviewed removal returning a genuine 404/410. Preserve media/PDF URLs or map them too. Cover trailing slashes, case, nested paths, pagination and relevant query variants. Avoid blanket redirects to the homepage, redirect chains, soft 404s and preview-host canonical URLs.

Compare meaningful rendered content, headings, titles/descriptions, canonical URLs, robots directives, language/hreflang and HTML language, structured data, social metadata, internal links, images/alt text, sitemaps and verification tags. Validate real HTTP responses and server-rendered HTML on the actual publish path, including service-worker behavior and tenant/host scoping. Staging should be access-restricted or explicitly noindex; remove deployment-time indexing blocks only for intended production pages.

Preserve essential forms, delivery destinations, validation, consent and analytics events. If commerce or memberships are used, require a separate reconciliation and transaction test before their cutover. Evaluate mobile layout, accessibility and performance on representative page types. Avoid combining the first migration with broad URL restructuring or content redesign.

Before cutover: no unexplained omissions in the ledger; all priority/search-landing URLs verified; assets and links checked; required forms work; source/target backups and isolated restore rehearsal pass; DNS/TLS/domain ownership and rollback are verified; changes since export are reconciled through a final delta or a scoped editing freeze. A rollback must account for new submissions/transactions and must not blindly restore possibly compromised WordPress code. Review the exact cutover plan before changing production traffic.

Track Search Console coverage/clicks/impressions, crawler responses, 404s, form delivery and performance after cutover. Preserve technical SEO signals as an acceptance goal; **zero ranking loss cannot be guaranteed**. Google describes both [hosting changes with stable URLs](https://developers.google.com/search/docs/crawling-indexing/site-move-no-url-changes) and [URL moves with potential ranking fluctuations](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes).
