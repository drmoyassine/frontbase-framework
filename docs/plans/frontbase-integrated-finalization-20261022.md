## 3. Ownership, coordination and change control

- Integration/deployment implementer owns the candidate manifest, target deployment proofs and final evidence matrix.
- Translation implementer owns Arabic recovery, coverage/route evidence, source-identity regressions and the approved live-data demonstration.
- One named operator owns mutations to a given staging service or test database at a time. Use the durable claim/ledger protocol; do not infer ownership from chat recency.
- Owner signs product scope/exclusions and separately authorizes production cutover, registry publication and any new persistent resource or destructive cleanup not already specifically approved.
- A reviewer checks conflict resolutions, security-sensitive changes and evidence. Where an independent reviewer is available, use one; otherwise explicitly record that review was self-review and retain reproducible fault evidence.

Use an isolated candidate checkout. Preserve the dirty shared checkout, both implementers' changes, private backups and existing tool files. No force push, rebase, reset, broad formatter or removal of unfamiliar diffs. Do not merge the translation branch back into the deployment branch just to create another integration history.

During candidate verification, admit only acceptance-blocking fixes. Every fix gets a source commit, affected regression, artifact rebuild where applicable, and a bounded impact assessment. Re-run affected gates; perform the cumulative candidate run on the final fixed source. A source or artifact change invalidates dependent evidence, not automatically every unrelated test.
