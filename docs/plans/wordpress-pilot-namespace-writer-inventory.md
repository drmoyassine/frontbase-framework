## Application state is distinct from a listing datasource

Application state stores `compat_pages`, versions, shared configuration, publication captures/reviews/pointers and recovery journals. The selected directory datasource stores institutions/programs/cities/articles. A connected Supabase listing source does not select the application-state driver or grant a transaction across both databases. No data/provider credential was read or changed during this inventory.

[Host state selection](../../examples/cf-full/src/state-db.ts) selects cloud Hyperdrive PostgreSQL in cloud mode; otherwise explicit memory/file/remote libSQL, a complete D1 REST configuration, a D1 binding, or Node's file default. Partial configuration refuses. File state is refused on Vercel Edge and Deno Deploy. [Backend](../../packages/backend/src/index.ts) also accepts an injected `makeRunner`; custom runners therefore need explicit capability acceptance rather than inference from a datasource kind string.

| State adapter / seam | Available evidence and limitation |
|---|---|
| `DbRunner` | [Contract](../../packages/edge-infra/src/providers/types.ts): query, exec, optional transaction. Exec returns a count where reported, otherwise zero. No declared atomic batch, lock, close, isolation, durable commit receipt or authoritative capability object. A method's presence is not hosted acceptance. |
| SQLite / libSQL memory, file and remote | [Runner](../../packages/edge-infra/src/providers/runners.ts) delegates each statement to `client.execute`; affected count is `rowsAffected ?? 0`. No exposed transaction/dialect. This diagnostic verifies current real local memory statements only. Native file commit and memory transaction behavior differ in the preceding investigation; remote/rollback/process-death guarantees remain unproved. |
| D1 binding | Individual prepared statement; number or `{count}` changes supported. No exposed batch/transaction in the framework's structural binding contract. Do not assume an underlying provider feature is available through this seam. |
| D1 REST | Separate HTTP requests; no transaction. Current exec extracts `meta.changes.count` only, unlike binding's dual shape. Accurate affected-count acceptance is a prerequisite before journal/CAS execution, not established here. |
| PostgreSQL application state | [State runner](../../packages/edge-infra/src/providers/postgres-state.ts) has a dedicated client for BEGIN/work/COMMIT, rollback on unsuccessful completion and rowCount. The transactional child has no nested transaction. A lost COMMIT response can remain uncertain. No host concurrency/crash proof supplied by this inventory. Migration code uses a PostgreSQL advisory lock specifically for migrations, not the page namespace. |
| PostgREST and Neon listing runners | [Factory](../../packages/backend/src/db/datasource-runner.ts) resolves these separately. Do not substitute these for application-state atomicity or broaden RPC privileges. Source inspection is not live Supabase acceptance. |

## Production writer coverage

Owner means the authenticated `tenant` in shared state, including a single self-host's owner namespace; it does not require a multi-site deployment. [Default-deny](../../packages/backend/src/mw/auth.ts) authenticates and attaches owner; it does not itself enforce an administrator role. Direct stores trust their caller to supply the owner.

## Implementation options for primary decision

These are proposals, not accepted architecture:

- A canonical owner/path claim table with database-enforced uniqueness can protect future create/rename/restore, provided all production writers atomically acquire/release claims with page mutations. Retain soft-deleted claims and special homepage identity; design canonical aliases deliberately. An advisory application lock alone does not stop legacy or arbitrary SQL writers.
- A proven transaction capability can make multi-page/config commit atomic on accepted runners. It still requires uniqueness plus conditional legacy writes; a paused old create can write after commit. Refuse unsupported drivers rather than sequential fallback. Native memory libSQL behavior prevents casually exposing its raw transaction API everywhere.
- A durable owner reservation and conditional per-step protocol could support nontransactional adapters, but each mutation must atomically prove operation ownership and reservation in its own database statement. Persisted intent/receipt cannot be inferred from equal content. No lease timeout may authorize takeover of uncertain work. This increases recovery/UI burden and requires driver-specific affected-count evidence.
- Retiring legacy console API removes its route writers on that host; it does not remove direct stores, compat writers, seeds or arbitrary connected datasource access. A new installer-only route with an advisory mutex would remain unsafe.

Before implementation acceptance: migrate-report existing duplicate/canonical aliases without deletion; create/create, create/rename, create/restore, homepage/boot, delete/recreate, tombstone/permanent-delete, conflicting installs and different-owner independence; gate all authenticated member/admin paths and direct store entry points; protected generic settings keys; concurrent config save/guarded page change/publication preparation/activation; owner edits between read/write; rollback after owner edit; accurate affected counts; commit/rollback/process death/lost replies/busy retries on chosen drivers; deliberate unchanged retry vs uncertain state; corrupted claim/journal refusal; offline restart and host acceptance. Namespace inventory supplies counterexamples, not these guarantees.
