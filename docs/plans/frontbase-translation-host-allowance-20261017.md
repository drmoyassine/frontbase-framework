## Reused paths and actual policy

[Host allowance](../../packages/backend/src/compat/translation-allowance.ts) composes the existing settings table, owned generation/storage resolvers, accounting HTTP adapter, neutral accounting policy and TranslationJobRunner. No new database, migration, credential store, scheduler, socket/native driver, public endpoint or package dependency. The engine's standalone compatibility path remains unchanged; this Frontbase composition requires accounting and has no unaccounted fallback.

The first supported unit is explicitly `provider-request`: one reservation per physical dispatch, immutable request count and concurrency ceilings, one attempt per reviewed job, at most100 exact reviewed intents, a maximum65536 UTF-8 bytes for the serialized messages and the configured output-token request cap. It is not a dollar allowance or a total token budget. There is no guessed price schedule, approximate tokenizer, currency picker or monetary guarantee. Pricing-backed monetary enforcement remains unavailable until verified conservative model bounds and dated pricing exist. Missing usage or ambiguous failure keeps the full one-request reservation and blocks automatic retry.

Review pins include the trusted tenant/project UUID, datasource/account identity and resolved HTTPS destination, storage settings revision, full generation configuration/revision, exact job intents and the allowance limits. A deterministic SHA-256 policy hash identifies this schema-validated content; host checkpoints contain no credentials or source text. This hash is an integrity/checkpoint identity, not a replacement for host authorization. The internal prepare function assumes its future administrative caller has reviewed those intents; no user-facing approval/start API is exposed here.

The host inserts one immutable project allowance checkpoint before creating the remote ledger, using the existing tenant-scoped settings uniqueness/conditional-write pattern. Identical preparation repairs the same remote allowance after a capability/network failure. A different allowance ID, changed limits or changed destination cannot overwrite it or silently allocate fresh capacity. A failed remote setup leaves that checkpoint in place. The return value contains only opaque allowance/hash/unit references.

Every authorization/reservation/dispatch rechecks the persisted pin; the provider wrapper checks once more before invoking AI. Model/locale/prompt/output settings changes, even a same-value settings save with a new revision, deny further dispatch. A queued job actually invoked after such a change records the existing terminal `denied` classification; durable batch pause/resume state is not implemented here. Underlying datasource URL/account retargets are also detected without depending on a settings revision. Credential rotation alone is not a destination change; credentials are resolved through existing ownership/encryption paths. The host run method captures trusted scope and accepts only a job ID; its returned scope is a copy and cannot retarget execution.

The existing [provider](../../packages/backend/src/compat/translation-generation.ts) and host byte limit share one message construction function. Source/context content is not counted using a different prompt approximation. No provider SDK retries or environment credential fallbacks are introduced. A configuration change after persisted dispatch but before the model call retains an uncertain reservation conservatively. Settlement and undispatched release remain bound to the original persistence session after a retarget, so incurred/uncertain usage cannot be erased by switching destinations. Cross-destination atomicity is not claimed; a change can race the final check and transport, so a dispatched request may still complete and incur cost.
