## Ordered implementation

### T1 — Shared provider invocation and configuration

First inspect actual account/model records, package exports and installed SDK capabilities. Add a versioned translation-generation configuration referencing an owned account/model, source/target locales, prompt policy/version and explicit limits. Reuse the storage settings ownership/CAS pattern; resolve credentials immediately before dispatch. Keep secrets, endpoints and private source text out of configuration/progress responses.

Create one injected server-only invocation service in the existing infrastructure layer and adapt TranslationAIProvider to it. Refactor workflow ai.chat to consume the same service where compatible, preserving standalone/workflow behavior through regression tests. The engine keeps its neutral provider port and no reverse dependency. Do not dispatch a fake workflow merely to invoke a model.

Start with one existing configured text-provider protocol proven by repository fixtures; expose other providers as unavailable until tested. Do not hardcode a new vendor, default model or global environment credential fallback for tenant translation. Normalize output, finish reason and usage; carry AbortSignal, output token cap and idempotency key where actually supported. Reject truncation, oversized output and broken protected tokens. Account for SDK retries: disable opaque retries or reserve/account each actual external attempt explicitly.

Acceptance: deterministic transport fixtures, owned/foreign/deleted account, key rotation, timeout/abort, unsafe URL/redirect, missing SDK/provider and response-size/format gates. Workflow and translation share transport tests. No real request required to finish T1.

### T2 — Durable allowance and attempt accounting before generation

Extend the existing engine persistence/runner with an injected accounting policy/port; no SDK pricing inside the translation engine. Add attempt and reservation records through the current adapter/protocol, scoped by tenant/project, batch, job and lease epoch. Store bulk attempt history in the selected translation destination; keep lightweight policy references/settings in the host. Implement matching deterministic/SQLite and HTTP protocol tests, without requiring SQLite in the edge runtime.

Use exact integer units for money/limits. A run pins provider/model, limits and a dated price schedule when reliable monetary estimates are available. Enforce maximum input/context size, output tokens, attempts, batch size and concurrency. Currency-based enforcement is available only with a conservative upper bound; otherwise show token/request ceilings and unknown cost, not a fabricated dollar guarantee. Existing plan quotas/rate limits remain independent constraints, not the translation spend ledger.

State flow: reserve atomically → persist dispatch intent → call provider → record result/usage → reconcile reservation → commit protected draft revision. Settlement must survive worker eviction and CAS rejection; a rejected translation can still have incurred provider cost. Cancellation releases only demonstrably undispatched reservations. Missing usage, timeout and a crash after dispatch retain an uncertain reservation/charge and require conservative recovery; never assume the call was free. Retry policy must not amplify ambiguous billing. Pin request and attempt IDs separately; do not claim exactly-once external charging from job idempotency.

Budget scope is explicit. Retargeting storage or changing settings cannot silently reset an active allowance: pause affected batches and require reconciliation/explicit new allocation. A limit for one Frontbase project is not an account-wide provider spending cap. Cross-destination transaction atomicity is not assumed.

Acceptance: competing workers cannot overspend a shared allowance; restart after every boundary; duplicated delivery/settlement; partial provider success; stale lease; cancellation; manual edit; changed source; pricing change; storage/account retarget; uncertain usage. Fault gates must detect bypassed reservation, duplicate release/settlement and tenant-scope removal.

### T3 — Small reviewable batch and durable execution

Use existing resource refs/context contracts to register an explicit selected page/menu text or selected live data field. Reuse published/draft ownership and field-selection metadata; avoid whole-record dumps or arbitrary public generation. Pin immutable source/context versions, target locale, provider/model/prompt and allowance in a reviewed batch intent. Existing source history is required for reproducible jobs and is not a frozen datasource snapshot feature.

Expose authenticated plan/start/status/cancel/resume operations using existing default-deny admin and tenant ownership patterns. Preview lists selected resources, item count, transmission scope, limits and known/unknown estimate. Start is the explicit content-transmission/spend action. Dry-run and account selection are free of generation calls. Persist all job intents before requesting delivery; bounded sweeps recover lost scheduling and use the existing job leases. Progress comes from persisted state, not process memory.

Scope delivery by authenticated host/project; queue payloads contain opaque IDs, not source bodies/credentials or client-chosen tenant identity. Validate callback signatures/shared-secret configuration, body/replay/destination bounds and owned queue configuration. If no durable scheduler is configured, explain it and support a bounded administrator-triggered continuation; never silently promise unattended completion from an in-process timer.

Acceptance: duplicate callbacks, queue failure after persistence, restart with no next public request, unauthorized callback, forged scope, cancellation/resume and deleted/reconfigured destination. Results are draft-only and manual corrections survive late work. Anonymous rendering never initiates AI.

### T4 — Settings and controlled end-to-end acceptance

Extend Translations with AI connection/model, locales, limits and batch status; reuse existing account connection screens and save/reload/CAS semantics. Show queued/running/complete/failed/cancelled/needs-reconciliation states in plain language, with safe item failures and charged/uncertain usage. Separate provider connectivity from actual translation generation.

Finish with one reviewed English → Arabic batch containing a few authored text units and a selected live-field fixture, writing only draft revisions. First run deterministic fixtures. A real provider test is credential- and spend-gated and records selected content, destination, maximum allowance and actual/uncertain use. Verify same/separate destination with isolated fixtures before changing real settings. No automatic bulk WordPress translation or live publication.
