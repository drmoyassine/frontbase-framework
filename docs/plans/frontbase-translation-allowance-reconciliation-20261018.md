## Lifecycle and reuse

[Host policy](../../packages/backend/src/compat/translation-allowance.ts) now records durable closing/closed state per policy hash in the existing tenant-scoped settings store. Existing checkpoints without a lifecycle row remain active for backward compatibility. Closing is monotonic and checked by the existing authorization, reservation, dispatch and last pre-call guards. A caller supplies the exact expected policy hash; a stale close cannot cancel a replacement allowance. The server-only function still requires a future authenticated administrative caller; a hash is not authorization.

Closing first freezes the host, then checks and cancels every existing reviewed job through the existing narrow HTTP job RPC. Cancellation fences the original persisted lease and any late revision write. Before releasing anything, it rereads jobs and requires terminal status, exact reviewed intent/scope and the current single-attempt/epoch policy. It also reads the corresponding accounting attempt. Missing/inconsistent dispatch evidence, failed cancellation/release, unexpected intent/epoch, corrupt state or an unreachable destination leave closing in place and block fresh allocation. There is no refund based on a local timer, cancellation alone or missing provider usage.

A persisted two-pass cursor separates cancellation from accounting proof. Each call performs at most four job steps across those passes, then CAS-saves progress for a fresh invocation. No timer or in-memory cursor is required. Concurrent/stale continuations cannot overwrite newer progress or a closed receipt. A delayed enqueue discovered during proof restarts fencing; no release bypasses the fence. Unknown consumption is considered only after proof reaches the final review stage.

Only a proven reserved, undispatched attempt can be released; the original accounting RPC remains authoritative. Settled requests count as consumed. Dispatched/uncertain attempts remain held by default and return a closing summary. An explicit `count-as-consumed` choice acknowledges each such request as one consumed request before closure. It never rewrites, refunds or deletes the original attempt. The closed receipt retains both total consumed requests and the count still unknown in the original ledger. There is no claim that an acknowledged external call has stopped, completed, cost nothing or become monetarily settled.

This remains a provider-request allowance, not a dollar ceiling or global provider-account concurrency cap. A new explicit allocation can coexist with an acknowledged old call that is still physically in flight; the old request remains recorded and held. Limits are per reviewed allocation. No automatic acknowledgment or background retry is introduced. A provider already in flight may settle later on the original ledger, while cancellation prevents its result from writing a draft. That later settlement does not rewrite the conservative closed receipt.

[Original storage recovery](../../packages/backend/src/compat/translation-storage.ts) reuses owned datasource/account resolution, encrypted credentials, guarded fetch, fixed schema and the existing accounting HTTP adapter. It resolves the original datasource ID and verifies the resolved endpoint/account/scope against the pinned identity. It does not route a fresh key to an arbitrary saved URL. Clearing/changing current settings or removing the current AI selection does not erase the original connection reference. Credential rotation is usable; deleting/retargeting that original connection blocks reconciliation until the original owned destination is available again. A failed initial remote ledger installation also remains blocking; no unsupported administrative abandon shortcut is provided.

Once the predecessor is closed, a separately reviewed allowance with a fresh ID can replace the active checkpoint using exact-value CAS. The predecessor's immutable plan is archived before replacement; lifecycle/receipts and the remote ledger remain. A losing contender cannot overwrite a newer allocation or create an extra remote allowance. Archived IDs cannot be resurrected, and the same closed allowance cannot be reopened by changing limits or configuration. Replacement itself is not generation authorization and does not enqueue work.

All operations reuse existing settings and job/accounting protocol1. No new SQL, migration, generic query RPC, credential store, native driver, queue service, package dependency or provider network call. Cancellation is terminal for existing jobs; a user-facing pause/resume model and generation UI remain subsequent work.
