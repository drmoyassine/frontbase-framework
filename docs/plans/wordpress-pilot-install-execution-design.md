# B installation execution: database and namespace prerequisites

**2026-10-08; evidence and implementation proposal, not a shipped executor.** Follows [artifact checks](wordpress-pilot-artifact-check-delivery.md), [destination checks](wordpress-pilot-install-check-delivery.md) and [guarded existing-draft changes](wordpress-pilot-draft-change-delivery.md). No new driver, migration, production transaction contract or public import format is adopted here.

## Observed adapter behavior

The existing `DbRunner.transaction` is optional. Current `libsqlRunner`, SQLite factory, D1 binding and D1 REST adapters do not expose it. The Postgres state adapter exposes a transaction with commit/rollback; that does not prove the same guarantee for PostgREST datasource access or every host. A datasource used for public listings is also distinct from the application's state database used for pages and journals.

A direct probe using the installed edge-infra libsql client created invented tables and committed one insert through `client.transaction('write')`. With `:memory:`, a subsequent query through the parent client returned `SQLITE_ERROR` because the table was unavailable. With a temporary file database, the subsequent row count was1. Installed native client source detaches the transaction connection and lazily creates a parent connection; exposing this API indiscriminately would alter in-memory behavior. The probe's Node cleanup failed with Windows EPERM; after the process exited, the exact resolved synthetic directory was inspected and removed with native PowerShell. Overall command exit1 is recorded, not presented as a passing transaction suite. No live state was accessed.

The file result proves only this local commit path. Rollback, failure after commit, concurrent writers, process death, remote HTTP/WebSocket libsql, busy handling, billing's optional transaction consumer and host bundles still need tests before changing the adapter. Do not silently enable transactions on every libsql client, fall back to sequential writes after failure, or claim D1/remote parity from this probe.

## Namespace race requiring repair

`PagesStore.create` inserts a page without a database slug uniqueness predicate. The route's prior slug lookup is a separate operation; updates can also change a slug independently. An installer transaction alone cannot make all legacy writers honor the new namespace. For example, a legacy request can observe an absent slug, pause, then insert after an installer commits a page at that slug. Existing destination preflight's post-probe read-back only detects changes during its own observation window.

Fresh real in-memory state proof used the current migrations and `PagesStore`: an absent-slug observation, creation of an invented installer page, then creation of an invented paused legacy page with a different ID and the same owner/slug. The final query returned two rows; the counterexample assertion passed with exit0. This reproduces the store-level interleaving, not an HTTP scheduler, transaction or safe installation proof.

Initial writer inventory: page create and metadata/slug update; layout save and version restore; soft delete, restore and permanent delete; homepage seeding; legacy publish/unpublish; the primary-auth-form direct update in page routes; guarded page-change writes; shared configuration CAS. Publication preparation/review/pointer transitions need explicit coordination semantics so an in-progress installation cannot be captured or exposed accidentally. All must retain existing owner/auth/no-leak boundaries. Read-only stores need no write lock. Raw test fixtures are not production writers, but the existing application seed paths are. Complete direct-SQL inventory and provider-specific acceptance still precede implementation.

Before installation is available, every path capable of creating, renaming, restoring or replacing a relevant page must respect an owner-scoped namespace protocol. Configuration writes and guarded draft changes must honor the same installation reservation while it is active. Claim ownership cannot follow from equal content, matching slug or a client receipt. Do not introduce a unique migration that silently deletes existing duplicates, or unconditional SQLite-specific triggers into portable state migrations.

## Ordered implementation and acceptance

1. Inventory all state runners and namespace writers. Define the capability needed for the chosen execution protocol and explicitly refuse unsupported runners. For a transaction adapter, prove real file commit/rollback, affected counts, callback lifecycle, concurrent/process failure behavior and existing billing regressions through the established runner seam.
2. Add owner-scoped namespace claims and installation reservation semantics. Preserve existing pages, deleted aliases and owner edits. Migration must refuse/report incompatible existing state rather than normalize or delete it silently. Prove paused legacy create/rename/restore interleavings, competing installs and distinct-owner independence before exposing install.
3. Compose artifact validation, destination bindings, required query/runtime/storage capabilities and namespace inspection on the server. Freeze exact destination-bound configuration/pages and digest; successful syntax/destination responses are observations, not execution receipts.
4. Persist original state, intended IDs and operation intent before writes. Atomically associate each completed mutation with server operation evidence. Lost replies require status/read-back; missing or ambiguous evidence never authorizes replay or adoption. Completed exact retries do not increment configuration revision.
5. Implement conditional recovery and restore, preserving subsequent owner edits and published state. Test interruption at every durable boundary in separate processes. No automatic lease expiry may let a second writer overtake an uncertain first writer.
6. Add review, install, status and explicit reconciliation controls inside the existing `/frontbase-admin`. Run fresh install and customization-preserving upgrade on the selected local state driver, then intended-host and separate-country reuse proofs. Do not use actual pilot publication to test install behavior.

The first executable implementation task is the adapter/writer capability inventory and its acceptance fixtures, followed by a proven owner namespace protocol. No owner input is needed for this bounded engineering work. Actual host acceptance, release edition/package acceptance, final packaging and production cutover retain their separate gates; off-server backup scheduling remains owner-deferred.
