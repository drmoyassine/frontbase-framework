### Receiver registration continuation

## Verified constraints

- The original private `relayTargetPolicy` validates one configured Cloudflare account/subdomain and one Vercel team. Its `connect` path permits only explicitly configured origins and deliberately does not run provider ownership verification for those enrolled origins. This is suitable for an operator's known installations, not arbitrary customers. `native-claim.ts` rechecks provider ownership before writes; retain that check.
- The relay ticket's receiver proof prevents replay, but the initiating receiver itself chooses the proof. It is therefore not, by itself, evidence that an arbitrary reconnect origin belongs to a previously verified installation. The new reconnect mechanism binds the verifier digest to the original verified project claim, exact origin and host; it still needs an independently verified live deployment and recovery/rotation story.
- The tested Cloudflare OAuth client is private to the owner's account. Cloudflare documents that public visibility requires a verified client domain, name, logo, client URL and scopes; public visibility is permanent. The private test client must not be represented as a public registration. See https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/.
- Vercel's isolated Unlisted integration supports the approved test projects. Public availability, integration branding/operating notices, permissions and a fresh installation in an independent team need confirmation. See https://vercel.com/docs/integrations/create-integration.
- `scripts/deployment-buttons.mjs` and the main README still point to `frontbase-selfhost-preview-20261026`; the reviewed hosted snapshot generator is explicit opt-in. The generated Cloudflare snapshot omits upstream workflow files to satisfy the provider GitHub app's actual permissions while preserving source CI.
