# Production hosted OAuth readiness — 2026-10-27

Status: **not production-ready**. Owner requests promotion of hosted setup to the main Cloudflare and Vercel buttons and a production OAuth service. The isolated native snapshots have live acceptance; the main buttons and general multi-tenant service do not. Do not expose the test relay as a production relay or silently replace its enrollment policy.

## Verified constraints

- `packages/backend/src/provider-oauth-relay-target.ts` validates one configured Cloudflare account/subdomain and one Vercel team. Its `connect` path permits only explicitly configured origins and deliberately does not run provider ownership verification for those enrolled origins. This is suitable for an operator's known installations, not arbitrary customers. `native-claim.ts` rechecks provider ownership before writes; retain that check.
- The relay ticket's receiver proof prevents replay, but the initiating receiver itself chooses the proof. It is therefore not, by itself, evidence that an arbitrary reconnect origin belongs to a previously verified installation. A public reconnect mechanism needs independently verifiable installation ownership and a recovery/rotation story, including cross-provider connections.
- The tested Cloudflare OAuth client is private to the owner's account. Cloudflare documents that public visibility requires a verified client domain, name, logo, client URL and scopes; public visibility is permanent. The private test client must not be represented as a public registration. See https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/.
- Vercel's isolated Unlisted integration supports the approved test projects. Public availability, integration branding/operating notices, permissions and a fresh installation in an independent team need confirmation. See https://vercel.com/docs/integrations/create-integration.
- `scripts/deployment-buttons.mjs` and the main README still point to `frontbase-selfhost-preview-20261026`; the reviewed hosted snapshot generator is explicit opt-in. The generated Cloudflare snapshot omits upstream workflow files to satisfy the provider GitHub app's actual permissions while preserving source CI.

## Required work before promotion

1. Define and implement a public relay admission protocol. Verify each native installation against fixed provider APIs and its consented account/project, bind its initial ownership claim to the provider-authoritative production origin and independently verified installation, and reject alias swaps, cross-tenant reuse, unauthorized provider changes, malicious URLs, replay and concurrent claims. Preserve existing private operator policy.
2. Design durable reconnect enrollment and secret rotation/recovery for already-activated installations, including Cloudflare, Vercel and Docker and connecting to a different provider. Do not treat a browser-supplied origin, installation ID or self-chosen verifier as sole ownership proof. Specify safe behavior after rollback, deletion and uncertain outcomes.
3. Qualify the production relay's secret management, retention and deletion, rate/abuse limits, backup retention, monitoring without token leakage, recovery, incident response and provider permissions. Provide accurate public operator contact and privacy/terms notices. Keep direct self-hosted registration possible without a required Frontbase service.
4. Register production provider clients at the chosen verified service domain, complete Cloudflare domain verification and provider publication steps, and verify external authorization from independently controlled accounts. Keep existing test integrations intact. Cloudflare's public visibility change is permanent.
5. Generate and publish a reviewed immutable hosted deployment snapshot with the production relay, update the main buttons and documentation together, and verify new independent CF/Vercel button deployments, external adapter selection, ownership, activation, admin creation, publication, upgrade and recovery. Include adversarial cross-account/recipient tests, real Docker consent, mutation/security suites and clean rollback. Do not count the previously approved isolated test accounts as independent multi-tenant proof.
