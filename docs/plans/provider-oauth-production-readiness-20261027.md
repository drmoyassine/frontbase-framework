### Receiver registration continuation

An opt-in public-native Worker and native receiver enrollment are implemented locally. After provider verification and durable native claim, the initial receiver verifier is stored as an encrypted/secret runtime variable on the target; the claim ledger retains only its digest, exact origin and host. For a later authenticated connection the installed server uses that key as the relay proof. The registry checks it before consent and again at redemption, including cross-provider connects; unregistered origins, wrong host, wrong proof, revoked registration and duplicate/replayed tickets are refused. Native Cloudflare/Vercel activation fixtures verify the key stays in secret or encrypted provider configuration and out of bootstrap receipts. Existing private mode remains available and unchanged. The public Worker fails closed without both provider clients and operator-supplied notices. This is local evidence only; it has not been deployed or verified using independent accounts.

The public-provider-verified install → registered reconnect sequence passes in the local SQLite/provider-double fixture. The relay security suite detects 22 faults, and the hosted-cloud suite detects five faults including acceptance of a plaintext registration key. The optional Worker rejects missing production notices/clients and unregistered receiver origins.

The key has no automatic rotation or self-service recovery. A production operator must provide a safe ownership-reverification and recovery procedure before depending on the public service; Docker enrollment and real Docker consent remain unimplemented. The registry is bounded to 100,000 claims in public mode and 1,024 in private mode. Tests cover host/origin/proof separation, pre-consent and redemption checks, secret propagation, public-mode refusal and 22 security mutations.

## Verified constraints

- The original private `relayTargetPolicy` validates one configured Cloudflare account/subdomain and one Vercel team. Its `connect` path permits only explicitly configured origins and deliberately does not run provider ownership verification for those enrolled origins. This is suitable for an operator's known installations, not arbitrary customers. `native-claim.ts` rechecks provider ownership before writes; retain that check.
- The relay ticket's receiver proof prevents replay, but the initiating receiver itself chooses the proof. It is therefore not, by itself, evidence that an arbitrary reconnect origin belongs to a previously verified installation. The new reconnect mechanism binds the verifier digest to the original verified project claim, exact origin and host; it still needs an independently verified live deployment and recovery/rotation story.
- The production Cloudflare OAuth client is public and domain verified; the separate isolated test client remains private. Cloudflare public visibility is permanent. See https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/.
- The production Vercel integration is Unlisted and works on the owner's approved test project; fresh installation in an independent team remains unverified. See https://vercel.com/docs/integrations/create-integration.
- `scripts/deployment-buttons.mjs` and README on the integration branch point to the hosted preview source; the default branch has not been updated. The named Git branch is mutable and its verified commit must be checked. The generated Cloudflare snapshot omits upstream workflow files to satisfy the provider GitHub app's actual permissions while preserving source CI.
