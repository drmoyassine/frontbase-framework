Frontbase Façade Audit

2026-08-21 repos: frontbase-framework · Frontbase- (product) trigger: silent Vercel engine deploy

A user deploys an engine to Vercel from the console; the API answers “Deployed successfully” in 25 ms and nothing exists anywhere. That one route turned out to be the visible edge of a pattern: every lifecycle verb that implies remote work in /api/edge-engines/* is local bookkeeping or fabrication, the codebase contains no deploy machinery at all, and the parity gate certified all of it. This report inventories what the product machinery actually is, classifies the framework surface against it, and traces exactly how the gate missed it.

1The finding, precisely

POST /api/edge-engines/deploy (packages/backend/src/compat/routes/edge-engines.ts:168) performs, in full: a tenant-scoped lookup of provider_id; one D1 insert whose entire config is a Fernet-shaped but unencrypted system_key; and {success:true, message:'Deployed successfully'}. No fetch is ever issued — the file never references externalFetch. The inserted row confesses at serialization time: url:'', provider:null, last_deployed_at:null (edge-shapes.ts:89–113) — a successful deploy of an engine that was never deployed.

The product’s equivalent (Frontbase-/fastapi-backend/app/routers/edge_engines.py:169) delegates to engine_provisioner.provision_and_deploy, which resolves the provider, templates the engine URL, runs quota and placement guards, upserts the EdgeEngine row, and hands off to engine_deploy.redeploy — build the bundle with tsup, push secrets before the first Vercel deployment, POST /v13/deployments, capture a source snapshot, flush the engine cache, sync the manifest.

The codebase already knows this is wrong

When the cloudflare deploy façade was removed, someone wrote into edge-misc.ts:336–346: “a false success is worse than an honest refusal.” That standard was applied to one route family. Seventeen engine-lifecycle ops and roughly seventeen satellites still return the false success.

2The machinery a faithful port must cover

The product’s deployment and edge-resource lifecycle lives in ~20 service files (≈8,000 lines) behind two routers. Its architecture is consistent and clean: provider-agnostic orchestrators dispatch through dict registries to thin per-provider adapters — never if/elif in routers. That maps directly onto the framework’s existing strategy-registry pattern, which already exposes discover / createResource / listEngines — everything except deploy.

The state model the framework’s store can’t hold yet

The framework’s edge_resources table is id, tenant_slug, kind, name, provider, config(encrypted text), status, created_at, updated_at — the entire lifecycle model. The product’s EdgeEngine additionally tracks url, adapter_type, is_active/is_system/is_imported/is_shared/is_managed/is_forked, source_snapshot, modified_core_files, bundle_checksum, config_checksum, last_deployed_at/last_synced_at, sync_status, and the move trio move_status/move_secret_hash/moved_out_at. In the framework these facts either don’t exist or are fabricated at serialization time (edge-shapes.ts hardcodes sync_status:'unknown', is_outdated:false, last_deployed_at:null…).

Architectural landmine: three load-bearing parts are process-based

“Faithful” cannot mean literal transcription, because the framework console runs inside a Worker:

  • Bundle builds shell out to npx tsup (or POST to a Docker edge-container’s /api/build-bundle). A Worker can spawn neither. The natural seam is the product’s own Docker mode: prebuilt bundle artifacts shipped with / resolved by the framework, with source-hash drift computed over the artifact.
  • Netlify deploys require the netlify CLI — Edge Functions’ eszip packaging has no pure-API path. Port options: a build service, or an honest refusal documented as such.
  • Scheduled jobs (90-day key rotation, stale-move pruning) run on Celery beat → map to Cron Triggers.

These are design decisions the port plan must make explicitly — and they interact directly with the framework-as-source-of-truth question.

4Gate forensics: how the parity gate certified all this

The conformance harness (packages/backend/test/compat-conformance.mjs; the “legacy” twin is byte-identical) is a serious piece of machinery. Its oracle is the vendored product OpenAPI plus a differential-evidence set; probes are synthetic requests; outbound fetch is stubbed to always-200. Its failure is not sloppiness but stacked alibis — each layer individually defensible, jointly vacuous for exactly the façade class.

How edge-engines/deploy passed, end to end

i

The probe only ever hits the refusal branch

Synthesized body {provider_id:'probe', worker_name:'probe'} → local lookup miss → 400. The fixture loop skips literal paths (no {param} to substitute), so the probe can never create a real provider first. The 200 branch — the actual façade — is never exercised by this gate.

ii

The refusal is “product-verified” because the product refused too

The differential corpus’s success-labeled deploy case used provider_id:'parity' — dead on both systems. “No difference between product and framework” ⇒ op enters productVerified ⇒ the probe’s 400 lands in PRODUCT_VERIFIED_REFUSAL, a bucket the gate tolerates unconditionally. Identical refusals to identical garbage inputs launder an op into “verified.”

iii

The behavior classifier scores the refusal functional via a 0-row read

Verified in source: the discarded-read check only runs when reads returned rows (compat-conformance.mjs:954); any handler whose only SQL is a lookup that finds nothing scores functional at :983–984 with the pinned evidence string “tenant-scoped state read reflected in the response” — false here; nothing was reflected. This exact string is pinned in contracts/behavior.ledger.json.

iv

And if the 200 branch were reached, the validator accepts any object

zod.gen.ts:1316: zEdgeEnginesDeployEngineResponse = z.record(z.unknown()), generated from the vendored spec’s {additionalProperties:true, properties:{}}. A success payload missing url, engine_id, and deploy_result parses as CONFORMS. 53 documented-2xx ops validate through vacuous schemas like this one.

Net damage inside the passing run

Of the 252 ops counted as “measured CONFORMS,” at least 10 are façade successes (reconfigure, sync-manifest, the four batch verbs, engine test, bundle-hashes, netlify-sites, vercel-projects) — validated by vacuous schemas and scored functional for writing local rows. The printed “75% measured, 0 violations” is, for the engine lifecycle, a certificate of nothing.

5Gate hardening, ranked

  1. Pin success-payload schemas from product recordings. Record real product 2xx bodies for the 53 vacuous-schema ops and diff framework bodies against them with the existing firstBodyDifference machinery. Kills the deploy/reconfigure/sync-manifest/batch class at the shape level.
  2. Add an EXTERNAL_REQUIRED assertion class. The providerTrace plumbing already exists: annotate ops that perform provider work, fail any 2xx with zero outbound calls, and assert target URL + method against a per-op allowlist. Deploy, engine test, Turso delete/test, site creates fail immediately and correctly.
  3. Close the 0-row-read hole. A lookup that returns nothing must not count as “state read reflected in the response” when the response is a refusal; classify refusal + lookup-miss as refusal. Then wire --require-functional into CI.
  4. Make PVR non-free. Move the 73-op list to a reviewed allowlist file; require each entry’s corpus case to have produced an actual product 2xx, not an identically-refused synthetic.
  5. Seed corpus prerequisites. The generator already supports {{provider_id}} variables — use them (plus the recorded stub) so the differential exercises success paths.
  6. Wire the gates that exist. Put --gate on the CI invocation (after fixing the 9 UNREACHABLE), add behavior and gate:cf22 to contracts.yml, and delete or make true the “includes --gate” comment. Stamp ledger entries with the differential-report hash so provenance is auditable.

6Port backlog

Ordered so each phase ends with behavior the hardened gate can actually certify. Sizes assume the registry pattern and the existing guardedExternalFetch / strategy seams.

P0 — make deploy real (the wizard path)

  • Decision required first: bundle strategy. Prebuilt artifacts (product’s Docker-mode equivalent) vs. build service. This gates everything else.
  • Port engine_provisioner (URL templates, guards, binding sync) + state-model columns (url, adapter_type, checksums, last_deployed_at…).
  • Port deploy adapters in risk order: Vercel (pure API, the user’s immediate need) → Deno (pure API) → Cloudflare (pure API) → Supabase (pure API) → Netlify (blocked on eszip; honest refusal if no build service).
  • Port /{id}/test and health-check as real probes (the sibling routes already show the pattern).
  • Ship alongside gate items 1–3, so the new surface is born certified.

P1 — lifecycle completeness

  • Real redeploy / reconfigure / batch verbs (delete the shared performBatch body).
  • Delete-with-remote-teardown (engine_test.delete_remote_resource registry) for engines + edge databases/caches/queues/vectors.
  • Domains via provider APIs with health-probe verification; real sync-manifest; real bundle-hashes from the artifact hash.
  • Fix the satellites: Turso ×3 (the strategy already exists), GPU test, storage site/project records.

P2 — the deep machinery

  • Secrets: secrets_builder env blobs + tenant-secrets push; key rotation with transition window (Cron Trigger for the schedule).
  • Logs: provider log APIs + persistence; the retention model.
  • Portable move: the full FBENG1 crypto protocol (the current fake-seal export with embedded plaintext secrets should be removed before any port — it’s a leak-shaped liability).
  • Fork/snapshot: deploy-time capture, is_forked/modified_core_files, snapshot builds (bound to the P0 bundle decision).

Method. Three independent audits: product machinery inventory (Frontbase- fastapi-backend, ~20 service files + 2 routers, read in full); framework compat-surface classification (every route in packages/backend/src/compat/, handlers quoted); gate forensics (harness source + replayed probes).
